# wrap-up: 작업 마무리 절차

목표: 이번 작업을 main에 안전하게 합치고(push → PR → 자동 Merge), 노션 작업 로그에 다음 사람이 이어받을 수 있게 기록한다.
사용자는 비전공자다. 각 단계를 한 줄로 알려주고, 아래 **"확인"** 표시가 있는 곳에서만 사용자에게 묻는다. 나머지는 끝까지 자동으로 진행한다.

## 1. 변경 확인
- `git status`, `git diff --stat` 로 바뀐 파일을 확인한다.
- 바뀐 것이 없고 push할 커밋도 없으면 "올릴 변경이 없습니다"라고 알리고 끝낸다.
- **올리면 안 되는 파일이 있는지 검사한다:** `.env`, 비밀번호·API 키가 들어간 코드, `model/data/` 의 데이터, `*.pt` `*.pth` `*.ckpt` `*.safetensors` 가중치, 50MB 넘는 파일. 있으면 커밋에서 빼고 이유를 설명한다.
- 내 파트 폴더 밖의 파일이 바뀌었으면 목록을 보여주고 의도한 것인지 **확인**한다.

## 2. 커밋
1. 파트: `git config --get fundamental1.part` (없으면 묻고 저장)
2. 브랜치: 현재 브랜치가 `main` 이면 커밋 전에 `git switch -c feat/<파트>-<짧은-영문-내용>` 으로 새 브랜치를 만든다. (main에 직접 커밋하지 않는다)
3. 커밋 메시지는 `[파트] 한 일` 형식으로 정하고 화면에 보여준 뒤 바로 진행한다. 파트 표기: [PM] [기획] [프론트] [백엔드] [모델] [공통] [배포]
4. `git add` (1단계에서 제외한 파일 빼고) → `git commit -m "..."`

## 3. main 최신 내용 합치기 (충돌은 AI가 확인 후 해결)
1. `git fetch origin` → `git merge origin/main --no-edit`
2. 충돌이 없으면 4단계로 간다.
3. 충돌이 나면 "다른 팀원의 변경과 겹치는 부분이 있어 제가 확인하고 합치겠습니다"라고 알리고 아래 순서로 해결한다.
   1. 충돌 파일 목록: `git diff --name-only --diff-filter=U`
   2. 파일마다 **양쪽의 의도**를 먼저 파악한다.
      - 내 쪽: 이번 작업에서 바꾼 내용과 이유
      - main 쪽: `git log --oneline HEAD...origin/main -- <파일>` 의 커밋 메시지, `git show <커밋> -- <파일>`, 노션 작업 로그의 해당 작업 항목("한 일", "다른 파트 영향")
   3. 해결 원칙
      - **양쪽 변경을 모두 살리는 것이 기본**이다. 한쪽을 지워서 쉽게 끝내지 않는다.
      - **다른 파트 폴더**의 파일은 main(그 파트 담당자)의 내용을 기준으로 두고, 내 변경은 꼭 필요한 부분만 그 위에 다시 적용한다.
      - `package-lock.json` 같은 **자동 생성 파일**은 main 버전을 받은 뒤(`git checkout --theirs <파일>`, 이 merge에서 theirs = main) 다시 생성한다. 예: `docker run --rm -v "<저장소경로>/frontend:/app" -w /app node:22-alpine npm install`
      - `requirements.txt`, `package.json` 의존성, 설정 파일은 양쪽 항목을 합치고 중복을 없앤다. 같은 라이브러리의 버전이 다르면 높은 버전을 쓴다.
      - 충돌 표시(`<<<<<<<`, `=======`, `>>>>>>>`)가 하나도 남지 않았는지 확인한다: `git diff --check` 와 `git grep -n -E "^(<<<<<<<|>>>>>>>)"`
   4. **사용자에게 묻는 경우 (예외, 확인):** 양쪽이 같은 기능을 서로 다르게 바꿔서 둘 다 살릴 수 없을 때(예: API 응답 형식을 서로 다르게 정함). 두 안을 쉬운 말로 비교해 보여주고 선택을 받는다. 판단이 어려우면 해당 파트 담당자와 상의하라고 안내하고, Merge하지 않은 채 PR 본문 "다음 작업자를 위한 메모"에 막힌 이유를 적어 PR까지만 올리고(노션에는 "PR 대기"로 자동 기록됨) 7단계로 가서 보고한다.
   5. 해결 후 `git add <파일들>` → `git commit --no-edit` (병합 커밋)
   6. 파일별로 "무엇과 무엇을 어떻게 합쳤는지" 한 줄씩 정리해 둔다. (노션 "충돌 해결 내역"에 기록)

## 4. 내 컴퓨터에서 실행 확인 (push 전 필수)
1. Docker Desktop이 켜져 있는지 확인한다 (`docker info`). 꺼져 있으면 켜 달라고 요청한다.
2. `docker compose up -d --build`
3. 확인 (PowerShell이면 `curl.exe`):
   - `curl http://localhost:8000/api/health` → `"status":"ok"`
   - `curl http://localhost:3000/api/health` → 같은 결과 (프론트 → 백엔드 연결)
   - 모델이나 predict 관련 변경이 있으면 `/api/predict` 도 호출
   - `docker compose ps` 에서 꺼진 컨테이너가 없는지, `docker compose logs --tail 50 <서비스>` 에 에러가 없는지
4. `docker compose down`
5. 실패하면 원인을 찾아 고치고 커밋한 뒤 다시 확인한다. 다른 파트 문제라 내가 고칠 수 없으면 Merge하지 않고 PR 본문 "다음 작업자를 위한 메모"에 막힌 이유를 적어 PR까지만 올리고(노션에는 "PR 대기"로 자동 기록됨) 7단계로 가서 보고하고 사용자에게 알린다.

## 5. push → PR → 자동 Merge
1. `git push -u origin <브랜치>`
2. PR
   - 이 브랜치에 열린 PR이 없으면 생성한다: `gh pr create --title "<커밋 제목>" --body-file <본문 파일>`
   - **PR 본문은 그대로 노션 작업 로그가 된다** (GitHub Actions가 옮김). `.github/pull_request_template.md` 의 섹션을 **모두** 채운다:
     무엇을 했나요(사용자가 이해할 수 있는 말로 3~5줄) / 어느 파트 / 바뀐 파일 / 확인 방법 / 다른 파트 영향 / 다음 할 일 / 충돌 해결 내역(3단계 정리, 없으면 "없음") / 다음 작업자를 위한 메모(왜 이렇게 했는지, 주의점, 임시로 둔 부분) / AI 도구(Claude Code 또는 Codex)
   - PR 제목은 `[파트] 한 일` 형식을 지킨다. 노션 "파트" 칸이 제목의 `[파트]` 로 정해진다.
   - 이미 있으면 번호와 링크를 가져오고, 본문이 비어 있으면 위 형식으로 채운다: `gh pr view --json number,url,body` → `gh pr edit <번호> --body-file <파일>`
3. **GitHub 실행 확인(CI) 기다리기:** `gh pr checks <PR번호> --watch`
   - "CI / Docker 실행 확인"이 통과해야 Merge한다. 실패하면 `gh run view --log-failed` 로 원인을 보고 고친 뒤 커밋·push → 다시 기다린다.
   - 다른 파트 문제라 내가 고칠 수 없으면 Merge하지 않고 상태 "막힘"으로 보고한다.
4. Merge: `gh pr merge <PR번호> --squash --delete-branch`
   - squash = 이번 작업의 커밋들을 하나로 묶어 main에 넣는다. `--delete-branch` 는 작업 브랜치를 지우고 main으로 옮겨 준다.
   - 그 사이 main이 또 바뀌어 Merge가 거부되면 3단계(합치기)부터 다시 한다. 최대 3번까지.
   - 브랜치 보호 규칙 때문에 리뷰가 필요하다며 거부되면 Merge하지 않는다. PR 링크와 함께 "리뷰 요청이 필요합니다"라고 알리고 상태를 "PR 대기"로 기록한다.
5. Merge 후: `git switch main` → `git pull` (gh가 이미 옮겨 줬으면 `git pull` 만). 로컬에 작업 브랜치가 남아 있으면 `git branch -D <브랜치>`.
6. main에 들어간 커밋 해시를 기록한다: `git log -1 --pretty=format:%h`

## 6. 노션 반영
1. **작업 로그는 AI가 직접 만들지 않는다.** PR이 열리면 "PR 대기", Merge되면 "Merge 완료"로 GitHub Actions(`Notion 작업 로그`)가 PR 본문을 그대로 옮겨 자동 작성한다. 그래서 5단계의 PR 본문을 빠짐없이 채우는 것이 중요하다. (노션 연결이 있어도 직접 만들면 중복되므로 만들지 않는다.)
2. Merge 후 기록이 됐는지 확인한다: `gh run list --workflow "Notion 작업 로그" --limit 1` 이 success 인지 본다. 실패했으면 `gh run view <id> --log-failed` 의 핵심 원인을 쉬운 말로 알려주고, 팀장에게 전달하라고 안내한다 (NOTION_TOKEN 설정 문제인 경우가 많다).
3. **노션 연결(MCP)이 있는 경우에만** 추가로 한다:
   - **할 일 보드 갱신:** 이번 작업과 관련된 내 파트 항목의 상태를 바꾼다. Merge했고 끝났으면 "완료", 일부만 했으면 "진행 중". 관련 항목이 애매하면 바꾸지 않고 보고에 적는다. "다음 할 일" 중 보드에 없는 것은 내 파트 "할 일" 항목으로 추가한다.
   - **API 명세 갱신:** "다른 파트 영향"에 API나 모델 입출력 변경이 있으면 노션 API 명세 페이지의 해당 부분과 "변경 이력"에 오늘 날짜로 한 줄 추가한다.
4. 노션 연결이 없으면 3번은 건너뛰고, 마무리 보고에 "할 일 보드에서 ○○ 항목을 '완료'로 바꿔 주세요", "API 명세의 ○○ 부분을 바꿔 주세요"처럼 사용자가 직접 할 일을 적어 준다.

## 7. 마무리 보고
- Merge 여부, PR 링크, GitHub 실행 확인(CI) 결과, 노션 작업 로그 자동 기록 결과, 다음 할 일을 짧게 보여준다.
- 충돌을 해결했다면 무엇을 어떻게 합쳤는지 한두 줄로 알려주고, 영향받은 파트 담당자에게 공유하라고 안내한다.
- Merge하지 못했다면 이유와 다음에 할 일을 알려준다.
